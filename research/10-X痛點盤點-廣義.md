- 調查範圍：X 公開貼文。關鍵字搜尋（Latest）＋語意搜尋＋已知事件串文。查詢時間約 2026-08-29。
- **排除**：密鑰／API key 推上 GitHub、帳單被刷爆——那類已在 `research/03-X社群需求盤點.md`。本檔只查其他類型。
- 網址規則：下列每則「已核網址」都用 `api.fxtwitter.com/<handle>/status/<id>` 抽過原文，帳號與 ID 對得上才寫。抽查結果見文末【自我審查】。
- 證據分層（全文遵守）：
  - **【實際查到・第一人稱】**＝發文者用「我／我們」講自己用 AI 寫 code／用 coding agent 時踩到的事。

### 2.1 @infinitelogins（Lovable＋Cursor＋Supabase，自己的 app 被黑兩次）

- 帳號：@infinitelogins（Harley Kimball）
- 貼文日期：2025-06-01
- 貼文網址（串頭）：https://x.com/infinitelogins/status/1929017755136561402
- 他實際說了什麼：

串頭：

> I vibe coded and shipped an app in three days. It got hacked. Twice. Here’s what I learned.  🧵

技術棧：

> The frontend connects to a Supabase instance, and I built it using Lovable and Cursor.

（https://x.com/infinitelogins/status/1929017756474814862）

第一次：以為 RLS 擋得住，24 小時內研究者能 insert／update／delete：

> Within 24 hours, a researcher showed they could insert, update, and delete records, even though the frontend didn’t expose those endpoints and RLS should have blocked it.

（https://x.com/infinitelogins/status/1929017763474944236）

原因是自己建的 PostgreSQL view 不吃底表 RLS：

> Why? The view I created didn’t respect RLS.
>
> By default, PostgreSQL views execute with the privileges of the view owner. In my case, this was an admin role. Unless you define the view as SECURITY INVOKER, or apply extra guards, RLS policies on underlying tables are bypassed. That was the critical misconfiguration.

（https://x.com/infinitelogins/status/1929017764943114543）

第二次：前端拿掉註冊，但 Supabase Auth 還開著，攻擊者可直接註冊成 authenticated user：

> This wasn’t due to the view. Instead, I had left Supabase Auth enabled, even though I had removed self-registration from the frontend. That meant attackers could still register via email/password and act as authenticated users, subject to whatever RLS rules existed.

（https://x.com/infinitelogins/status/1929017767677800667）

影響範圍他自己寫：

> Threat modeling matters. My app only handled public data, so the impact was low. If you’re handling PII/PHI, this kind of exposure could be catastrophic.

（https://x.com/infinitelogins/status/1929017769024180551）

- 造成什麼後果：被黑兩次；作者自述資料是公開目錄、衝擊低。沒寫金額。串頭抽查時約 3,646 likes、約 811,681 views。

**本類搜尋觀察（不是第一人稱證據）：** Latest 關鍵字幾乎被「我審計過 N 個 Lovable／Bolt app、XX% RLS 沒開」的獲客文佔滿。那些數字見二手來源，不能當成受害者本人發文。

## 方法與限制

- 工具：X 關鍵字搜尋（Latest，每query 最多 10 則）、語意搜尋、已知事件 `from:jasonlk` 日期窗、串文展開。單一類別搜超過約 5 分鐘仍不足 3 則就停，不硬湊。
- 沒有登入 X、沒有搜鎖推。刪文、鎖推、改 handle 的舊事件會漏。
- Latest 演算法偏新文，所以 2025 年 Jason／Harley 是靠已知帳號＋日期窗才挖到；2024 以前可能還有，本次沒系統回溯。
- 低互動第一人稱（0 like）仍然收錄——跟 `03` 同一標準——但**不**把低互動寫成「社群共識」。
- 推測 vs 查證：
  - **查證過**：下面【自我審查】列出的網址，HTTP 200，handle／id／原文對得上。
  - **推測**：第 2／4／5／6 類「其實很多但不發 X」——**沒有證據**，只能寫「公開第一人稱不夠」。審計帳號的百分比未經本次複驗。
