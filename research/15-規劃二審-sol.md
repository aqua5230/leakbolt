# LeakBolt 規劃二審（sol）

## 總判斷

**風險類型沒有砍過頭；付費價值仍未被證明。** 現在不該為了填滿階段三，硬塞另一種漏洞。真正缺的是兩件事：把同一次密鑰事故處理到可核對的終點，以及證明目標使用者願意為這個流程付 $39。

另外，現行「第一人稱證據為 0 就不做」會把未被察覺、難以公開、剛出現的風險全部判成不存在，應撤回一票否決地位。

## 1. 現在的範圍撐得起 $39 嗎？

### 結論

**有機會，但目前證據只支持做產品，不支持 $39。** 價格不由功能種類數決定。一宗外洩的損失足以讓 $39 合理；但 `research/10` 證明的是事故存在，不是使用者願意付費，也沒有證明桌面介面比免費 CLI 多出的價值值 $39。

因此，不缺「第三種漏洞」；缺的是付費價值證據與更完整的事故閉環。應先做有價格的假門測試、可退款預購或 10–20 人付費陪跑。成功條件是實際付款或押金，不是稱讚、候補名單或訪談中的意願。

### 可補、且不違反判準表的內容

以下仍是密鑰／憑證同一事故，不擴成通用 AppSec：

1. **Git 暴露地圖**：列出命中存在於哪些 branch、tag、stash、reflog、worktree、submodule 與本機孤立物件；顯示最早出現時間與仍可到達的位置。全部可離線、可重現。
2. **限定範圍的清理證明**：處理後產生本機報告，逐項寫明掃過哪些 Git 表面、哪些已清、哪些仍在、哪些只能由使用者去供應商端確認。不能寫成「密鑰安全」或「事故已完全修復」。
3. **憑證檔隔離交易**：只對整個已追蹤的憑證檔做預覽、備份、移出 index、補 ignore、失敗回滾；不要順手改任意原始碼。
4. **離線健康盤點**：找出 hook 已失效、規則過舊、長期未掃與新增 repo，並讓使用者一次修復安裝狀態。這比再加一個弱證據漏洞更接近付費桌面版價值。

有一刀其實還沒砍完：**「一鍵移進 `.env`」若包含改寫原始碼，仍是架構改寫。** 工具無法通用地決定環境變數名稱、client/server 邊界、載入方式與部署設定。安全範圍只能是「整個 `.env`／憑證檔誤被追蹤」的 Git 操作；程式碼中的字串只能給 diff 預覽與框架限定配方，不能承諾通用一鍵完成。

## 2. 「第一人稱證據為 0 就不做」有沒有問題？

### 結論

**有，而且是結構性問題。** `research/10` 的 0 只代表「一次有時限、偏近期、只查公開 X、找不到受害者自述」，不等於事故率為 0。其方法也明載：每類約五分鐘停損、未登入、會漏刪文與鎖文、舊事件回溯不完整。把這個 0 當否決票，是把搜尋限制誤當市場事實。

第一人稱貼文另有四種偏差：受害者可能不知道自己中招；企業受保密與法律限制不發文；新風險尚未累積受害者；嚴重事故反而更少公開。它適合證明「痛感與用語」，不適合單獨判定技術風險是否存在。

### 替代判準

改成三道門，不再數單一來源：

1. **產品適配門，四項全過**：能純本地判定；命中條件可寫成測試；誤報可用固定語料庫量；能沿用現有阻擋與處理流程。
2. **存在性門，至少兩種獨立證據，且至少一種是實測**：可重現攻擊或失敗案例、官方 advisory／CVE、公開資料集的盛行率研究、自己對盲樣本 repo 的掃描、目標使用者的 issue／客服紀錄、第一人稱事故。廠商行銷稿與同源轉載只算一種，不能湊票。
3. **出貨門**：固定真／假樣本集達到預先寫定的誤報與漏報上限，再由目標使用者 beta 驗證處理流程。要列入付費版，另須有付款、押金或已定價試點；技術風險成立不等於有人會買。

對剛出現但高衝擊的風險，可先進「觀察／原型」軌：只要可重現、目標族群確實暴露、最壞損失高，就能研究，不必等受害者發文。未過出貨門前不預設開啟，也不放進安全承諾。

## 3. 不上傳資料，怎麼量階段一指標？

### 結論

**若「任何資料都不離開裝置」是字面硬規則，公司不可能取得跨使用者指標。** 下載量只能量下載，無法推出啟用、留存、誤報或繞過。這不是實作技巧能解的問題。

可執行方案是把正式產品與研究 cohort（研究樣本）分開：正式版零 telemetry（遙測，程式自動回傳使用資料）；封閉 beta 由使用者明確加入，所有事件先存在本機，30 天後預覽並手動提交只有計數的摘要。文案必須改成：「產品不自動上傳；程式碼、密鑰、路徑、檔名、repo 名稱、remote URL 與原始命中永不離機；測試者可自願提交預覽過的統計。」如果連統計也不得離機，就刪掉這些晉級指標，改做實驗室相容測試與訪談，不能假裝量得到。

### 本機紀錄

每次安裝產生隨機 salt，只留本機。`repo_key = HMAC(salt, canonical_git_dir)`；`repo_key` 與 salt 都不匯出。SQLite 只記：日級時間、OS 大類、hook adapter、事件類型、成功／錯誤碼、耗時 bucket、規則 ID、不可逆命中指紋、使用者分類與後續複掃結果。不得記 path、檔名、commit 內容、remote、原始 secret 或完整 commit hash。

提供三個明確操作：

```text
leakbolt study enroll
leakbolt metrics show
leakbolt metrics export --since 2026-09-01 --output leakbolt-summary.json
```

`export` 只輸出總數與分組總數；先在畫面逐欄預覽，使用者再自行提交。小於 5 的 OS／adapter 分組併入 `other`，避免稀有組合反推出個人。

### 六項指標的可觀測定義

1. **啟用 repo 數**：安裝驗證成功，且至少完成一次真實 staged scan 的本機 `repo_key` 數。只執行 `install` 不算。
2. **30 天留存**：第 0 天啟用的 repo 中，第 24–37 天健康檢查仍通過，且期間至少有一次掃描的比例。由第 30 天本機快照直接輸出分子與分母，不匯出 repo_key。
3. **hook 成功率**：安裝後以 `LEAKBOLT_VERIFY=<random_nonce>` 執行 `git hook run pre-commit`；舊版 Git 則直接執行解析後的 hook entrypoint。只有 canary 回寫相同 nonce 才算成功；`verified_success / install_attempt`，按 OS 與 adapter 分組。另在暫存 repo 做一次真正的無秘密 commit。GUI Git 客戶端仍須具名測試矩陣，不能由 CLI 成功率代替。
4. **誤報率**：使用者把命中標成 `real secret`、`false positive` 或 `unknown`。主指標用 `false positive / 已分類命中`，另報 unknown 比例；`false positive / 掃描次數` 只能叫「每次掃描誤報數」，不能叫誤報率。
5. **處理完成率**：被標成 real secret 的事件中，同一不可逆指紋在處理後複掃消失，且所有已列掃描表面皆無命中的比例。供應商端 revoke 無法離線驗證，只能另列「使用者確認已 revoke」，不可混成技術驗證。
6. **`--no-verify` 率**：**精確值量不到。** `--no-verify` 讓 hook 完全不執行，hook 不可能替自己的缺席記錄。可量的替代項是「未掃 commit 率」：pre-commit 在本機 ledger 記錄 `git write-tree` 的 tree OID；健康檢查再比對新 commit 的 tree OID，計算無對應成功掃描的 commit／全部新 commit。tree OID 不匯出。這仍會混入 hook 被覆寫、其他機器產生的 commit 與 GUI 繞路，因此名稱不能寫成 `--no-verify`。精確 `--no-verify` 只能在受控可用性測試中觀察，不能當實際產品指標。

解除安裝也同理：正式 uninstall 事件只抓得到正常移除。手動刪 hook 要靠第 30 天健康檢查歸為「不再受保護」，不要稱為精確解除安裝率。

## 4. 哪個已知缺口最可能動工後才爆炸？

**第 1 個：hook 覆蓋與共存。** 它最危險的地方不是安裝失敗，而是安裝當下成功、之後被套件安裝程式、GUI client、worktree 或另一套 hook manager 靜默改掉。開發機上的單元測試容易全綠；真實使用者跨 OS、shell、Git client 與既有工具的組合，才會出現長尾。

它還會污染整套驗證：沒有 hook event，可能代表沒 commit、用了 `--no-verify`、hook 被覆寫或 client 根本沒走該路徑。團隊會同時失去保護與量測，卻可能誤以為留存很好。因此應在寫完整介面前，先用實際 commit 建相容矩陣與故障注入測試：安裝後改寫 `core.hooksPath`、重裝 Husky／lefthook、建立 worktree、從目標 GUI commit，再看能否偵測失效。過不了就先縮支援矩陣，不能只加免責文案。

## 5. 還有哪些會擋路的空白？

### 5.1 缺威脅模型

工具會掃不受信任的 repo、改 hook、讀 Git 物件，桌面版還會遍歷整台機器。尚未定義惡意 symlink、惡意 repo 設定、超大物件、submodule、嵌套 repo、hook shell injection 與權限邊界。這是安全產品自己的攻擊面；應先列資產、信任邊界、可寫位置與禁止執行的 repo 內容。

### 5.2 缺偵測品質基準

沒有版本化的真陽性、假陽性、已作廢格式、範例值與大型 repo 語料庫，就無法定義「誤報壓下來」，也無法安全更新規則。先建立可公開重跑的 sanitized corpus（去敏語料庫）與每版 release gate；使用者分類只能補充，不能當唯一真相。

### 5.3 免費版與付費版尚未形成可驗證假設

若免費版已完成攔截、歷史掃描與主要處理，付費版可能只剩「同件事比較漂亮」。這不一定賣不動，但現在沒有假門、預購、價格訪談或退款條件。應在 GUI 大量開發前，用同一批真實事故流程測試三個方案：免費 CLI、自助桌面版 $39、人工陪跑 $39；看誰真的付款與完成處理。

### 5.4 付費、授權與更新和零連線承諾互撞

直售 app 要決定下載授權、換機、退款、離線啟用、更新通知與被盜版時的取捨。若 app 驗證 license 或自動查更新，就已有 revoke 頁面以外的連線；若完全不連線，就應明定 DRM-free（無數位鎖）、手動下載已簽章更新與可驗證 checksum。這要在選商店與 updater 前拍板。

### 5.5 缺失敗與復原規格

安全工具卡住 commit 時，掃描器 crash、規則損壞、磁碟滿、權限不足與更新失敗要 fail-open（失敗仍放行）還是 fail-closed（失敗就阻擋），目前沒有逐情境決定。兩種都會傷害核心承諾。應為每個失敗模式明列預設、錯誤訊息、診斷資料、復原命令與是否允許暫時繞過。

## 自我審查

- 五題都有明確結論；第 3 題含本機資料模型、操作命令、六項公式與不可量項目。
- 已刪除只重述既有路線圖的段落。保留的既有項目只用來指出新衝突：通用 `.env` 改寫、絕對零資料與集中指標、零連線與付費更新。
- 證據與判斷已分開：`research/10` 的搜尋限制屬文件事實；$39 可售性、最可能爆炸的缺口與新增門檻屬本輪判斷。
- 未用第一人稱貼文數推導市場大小，也未把「找不到」寫成「不存在」。
