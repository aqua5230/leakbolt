# 一、路徑審查

**結論：楔子成立，終局也不是致命錯誤；致命缺陷在中段。現行規劃把「快速、確定、可逆的攔截」直接接到「替使用者重寫前後端架構」，再接到需要持續更新的漏洞資料。這兩次跳躍都沒有被階段一驗證，且會破壞前面已承諾的確定性、低誤報、純本地與 $39 買斷。若不改，產品會在尚未證明付費意願前，先變成高支援成本的半套 AppSec 工具。**

### 路徑本身為何仍可走

可延伸的共同核心不是「密鑰」，而是同一個行為：**在不可逆邊界前，對可明確判定的風險做阻擋，並留下可驗證的處理結果。** 密鑰、`.env`、憑證檔與部分已知危險設定都能沿用同一套「掃描 → 阻擋 → 處理 → 複掃」流程。這與既有「只說我擋下了什麼」的承諾一致，不必推翻階段一。[依據：`PLAN.md`「〇、終局」「一、判準」；`DECISION.md`「三、產品方向」；`research/03-X社群需求盤點.md` §4.1]

但終局文案「AI 寫的 code 進 repo 之前，那道確定性的閘門」仍太容易被讀成全面檢查。對外每次都應列明當下涵蓋的事故類型，不能把團隊內部的「AI 時代資安專家」變成覆蓋全部安全問題的暗示。否則會碰到已拍板的「不可製造錯誤安全感」。[依據：使用者本次澄清；`PLAN.md`「〇、終局」與兩條硬規則；`DECISION.md`「三件不能忍」第 2 條]

### 兩個斷點

1. **階段一 → 階段二斷在「一鍵修掉前端洩漏的 key」。** 找出硬編 key 是確定性檢查；把 API 呼叫搬到後端不是。它涉及框架、部署商、認證、權限、資料流、伺服器成本與測試，可能修壞功能，也可能造出沒有存取控制的公開代理。這不是桌面 GUI 對 CLI 的自然升級，而是從掃描產品跨進程式碼改寫產品。階段一的安裝數、誤報與密鑰攔截使用資料，不能驗證使用者是否信任產品改架構。**現況違反** `PLAN.md`「判斷性功能逐案評估」及「不承諾控制不了的結果」；也與 `research/03` 指出的「前端外洩聲量大」混淆：痛點強，只證明要解，不證明「一鍵搬後端」可安全交付。[依據：`PLAN.md`「一、判準」「階段二」；`research/03-X社群需求盤點.md` §2.1 卡點 C、§4.1；`DECISION.md`「三件不能忍」第 2 條]

2. **階段二 → 階段三斷在「lockfile 對已知 CVE 比對」。** 比對套件名稱與版本可以確定；判斷是否可利用、應升哪版、升級會不會破壞產品，不是。離線漏洞庫還會迅速過期。若承諾持續有效，就需要更新來源、發布管線、簽章、回滾與維護期限；若不更新，就會再次製造錯誤安全感。**現況違反** `PLAN.md`「核心掃描零連線，唯一允許連線是開 revoke 頁面」的既有規則。這項功能也把產品從密鑰處置的明確缺口拉進已有成熟工具的依賴漏洞市場，現有研究沒有證明同一批人要它。[依據：`PLAN.md`「階段三」「技術基座決定」；`research/01-開源競品-gitleaks生態.md`「專案缺點與局限分析」；`research/03-X社群需求盤點.md` §4.3]

### $39 買斷能不能撐到終局

**不能。它只能撐一個邊界固定、維護期明示的本地 v1，撐不起永久增加規則、修復器、AI 工具介面、平台與漏洞資料。** 「純本地沒有每次掃描的伺服器成本」不等於沒有持續成本；研究、規則更新、作業系統相容、簽章、公證、客服與發行都會持續發生。`research/04` 已列出每年簽章成本，`research/01` 也顯示競品與 AI 工具介面仍在快速更新。[依據：`DECISION.md`「商業模式」「可擴展邊界」；`research/01-開源競品-gitleaks生態.md` §1、§4；`research/04-平台與簽章成本.md` §2–3]

建議保留「買斷後該版本永久可用、程式碼不上傳」；刪掉「同一買斷版本持續變厚」的無限承諾。改成購買前寫清楚安全修補期，重大新檢查與新修復器放入付費大版本。若團隊版後來成立，訂閱收入可以補共享服務成本，但在團隊需求未驗證前，不可把它當作個人版研發的資金來源。[依據：`PLAN.md`「階段三」「階段四」；`research/06-安裝方式與平台決策.md`「可擴展邊界」]

### 階段門檻判定

- **1,000 次安裝：太鬆，而且定義錯。** 套件下載、重裝、CI 下載都可能灌高數字；它不證明 hook 有成功觸發、使用者沒有繞過、事故有被正確處理。「回報的誤報中位數 ≤ 1」也有自選回報偏差，且沒有除以掃描次數或真警報數。1,000 可保留為觸及指標，不能當晉級門。晉級應看可識別的啟用 repo、30 天後仍受保護、各目標 OS／Git 客戶端的 hook 成功率、每次掃描誤報率、攔截後完成處理與複掃的比例，以及停用／`--no-verify` 率。數值應由原型測試先建立基線，現有研究沒有支持 1,000 這個切點。[依據：`PLAN.md`「階段一」；`research/03-X社群需求盤點.md` §3、§4.2；`research/05-使用者OS與hook衝突.md` §1–2]

- **2% 轉換率：太鬆，且分母錯。** 1,000 次安裝即使全是可聯絡的真人，2% 也只有 20 筆訂單，按 $39 計為 **$780 毛收入**；這不足以驗證可持續公司，只能算有人願意付錢。CLI 是三平台，付費版卻只有 macOS，拿全部 CLI 使用者當分母還會低估真實轉換。應改看「符合 macOS、實際啟用且遇過處置流程的使用者」轉換，並以能否覆蓋事先列出的維護與獲客成本判定，不先拍一個無成本模型支撐的百分比。[依據：`PLAN.md`「階段一」「階段二」；`DECISION.md`「商業模式」「平台」；`research/04-平台與簽章成本.md`]

- **15% 主動詢問團隊功能：不是太鬆或太緊，而是失真的門檻。** 「主動詢問」受介面與訪談方式影響，沒有詢問不等於沒需求；有詢問也不等於願意付。若前一門只產生 20 位買家，15% 只要 3 人留言就可能觸發一條新產品線，絕對證據又太弱；單筆 20 席詢價同樣可能只是探索。應要求不同組織願意進入有價格的付費試點，並確認共享例外、集中報表或稽核確實是採購阻礙，再開團隊版。[依據：`PLAN.md`「階段四」；`research/02-商業競品與定價.md` §1；`research/06-安裝方式與平台決策.md`「可擴展邊界」]

**判斷會反轉的條件：** 若原型資料證明使用者把 LeakBolt 視為可信的程式碼改寫者、前端搬遷可在少數受控框架內高成功率通過測試，且付費大版本或團隊收入已能覆蓋持續維護，上述中段與商業模式否決才會反轉。現在沒有這些證據。

# 二、命名方向

**結論：首選「工業安全聯鎖」，次選「放行／檢定」。不要再以洩漏物件命名，也不要以籠統的安全名詞命名。名字應描述產品長期不變的動作：條件不合就不放行。這能從密鑰延伸到憑證檔、危險設定與其他確定性檢查，又不暗示包辦全部資安。**[依據：使用者本次方向澄清；`PLAN.md`「〇、終局」「一、判準」；`research/07-商標查核.md` §2]

以下只評語意，不評網域、套件或商標可用性。既有硬否決規則 `*guard` / `*shield` / `secret*` / vault / sentry / keeper 全部保留。[依據：`DECISION.md`「產品名稱」硬否決規則]

### 1. 工業安全聯鎖——首選

它表示機器只有在安全條件成立時才能進下一步，最貼近「確定性判定＋阻擋」，也不限定檢查種類。語氣偏工具與基礎設施，適合長成多種本地閘門。具體字詞：**Interlock、Cutoff、Relay**。[依據：`PLAN.md`「一、判準」；`DECISION.md`「四個必要能力」]

### 2. 放行／檢定——次選

它強調檢查完成後取得通行資格，能自然承接「掃描 → 處理 → 複掃」。比「安全」更可證明，也容許產品明說只檢了哪些項目。具體字詞：**Clearance、Attest、Preflight**。[依據：`DECISION.md`「止血閉環」；`PLAN.md` 兩條硬規則]

### 3. 閘門／關卡——可用，但較泛

它最容易讓人理解會阻擋 commit，也能延伸到 pre-push 或 CI；缺點是只說「擋」，沒有說依什麼放行，容易落入泛稱。具體字詞：**Gate、Checkpoint、Threshold**。[依據：`PLAN.md`「〇、終局」；`research/03-X社群需求盤點.md` §4.1]

### 4. 驗證／證明——可用，但要避免過度承諾

它適合結果頁與檢查報告，長期也可容納多種規則；但單獨使用可能被理解為「已證明安全」，與不製造錯誤安全感衝突。若採這方向，文案要固定限定為「通過列出的檢查」。具體字詞：**Verify、Proof、Certify**。[依據：`DECISION.md`「三件不能忍」第 2 條；`PLAN.md`「不承諾我們控制不了的結果」]

### 5. 邊界——不建議作主方向

它有延展性，卻偏被動，沒有表達「不合格就中止」；也容易被理解成網路邊界產品，與本機 commit 邊界不夠直接。具體字詞：**Boundary、Perimeter、Verge**。[依據：`PLAN.md`「終局」；`research/01-開源競品-gitleaks生態.md`「空位判斷」]

「檢查清單」也不建議。Checklist、Review、Audit 都像提示或事後報告，不像強制閘門；`research/03` 已證明太晚、太吵、可忽略的提醒正是現有工具的失敗形態。[依據：`research/03-X社群需求盤點.md` §3、§4.2]

名字本身不要放 AI。AI 是來源情境，不是穩定能力；放進名字會縮短品牌壽命，也會讓非 AI 產出的同類事故看似不在範圍。名字也不要放 leak、key 或 secret，否則仍會重演 LeakBolt 的語意鎖死。[依據：使用者本次方向澄清；`PLAN.md`「落在框裡的功能」]

# 三、漏掉的阻礙

**結論：規劃目前低估的不是掃描引擎，而是覆蓋、修復安全、更新供應鏈、延遲與信任。任何一項沒處理，都會讓「已裝＝被保護」變成新的錯誤安全感。**

### 1. Git hook 不是不可繞過的產品邊界

**為什麼會擋：** `--no-verify`、未經 Git 的部署、部分 GUI 客戶端、Web 型 AI builder、hook 被其他工具改寫，都可能繞過 pre-commit。Windows 的 shell 執行差異與 `core.hooksPath` 衝突已被查實。若首頁稱「進 repo 前的閘門」，這些缺口會直接傷害承諾。[依據：`research/05-使用者OS與hook衝突.md` §1.2、§2；`research/06-安裝方式與平台決策.md` §1–2；`research/03-X社群需求盤點.md` §2.1 卡點 D]

**怎麼繞：** 把 per-repo hook 定位為第一層，不宣稱不可繞過；提供可選的 pre-push 與 CI 同一掃描命令、安裝健康檢查、hook 被覆寫提示，以及清楚列出的未覆蓋路徑。CI 只在使用者自己的 runner 內掃，不把程式碼送到產品伺服器，仍可守住本地資料承諾。

### 2. 「移進 `.env`」不等於修好

**為什麼會擋：** `.env` 可能早已被 Git 追蹤；某些前端框架會把特定前綴的環境變數編進瀏覽器 bundle；已進歷史的 key 即使搬走也必須作廢。自動改引用還可能讓應用程式壞掉。把它叫一鍵修復，會重演使用者「刪檔就安全」的錯誤認知。[依據：`research/03-X社群需求盤點.md` §1.2 第 4–5 則、§2.1 卡點 C–D、§4.2；`research/06-安裝方式與平台決策.md` §1.2]

**怎麼繞：** 把流程拆成狀態機：先判斷是否曾進歷史；若曾進歷史，先要求 revoke；再檢查目標框架的 client/server 環境變數規則；顯示修改差異；執行既有測試；最後掃 index、history 與 build 產物。無法證明安全的步驟只給引導，不標「已修復」。

### 3. 規則與漏洞資料本身是供應鏈

**為什麼會擋：** gitleaks 鎖版提供穩定基線，但新供應商、新 key 格式與新 AI 工具會繼續出現。規則若不更新會漏報；自動更新若被竄改，掃描器本身就成為攻擊入口。離線 CVE 庫的問題更嚴重。[依據：`DECISION.md`「技術基座」；`research/01-開源競品-gitleaks生態.md` §1、§4；`PLAN.md`「階段三」]

**怎麼繞：** 在動工前定義簽章規則包、版本固定、回滾、來源追蹤、誤報回歸測試與支援期限。更新由使用者主動觸發或隨已簽章版本發布；不要在未改既有網路規則前偷加背景連線。若無法長期維護 CVE feed，就不做該項。

### 4. Commit 延遲會把強制閘門變成停用按鈕

**為什麼會擋：** install 時全歷史掃描合理，但每次 commit 若混入歷史、依賴資料庫或多種規則，延遲會隨 repo 放大。`research/03` 已顯示設定成本與警報疲勞會讓使用者規避工具；效能不佳會產生同樣結果。[依據：`DECISION.md`「四個必要能力」「安裝方式」；`PLAN.md`「階段一」；`research/03-X社群需求盤點.md` §3.1]

**怎麼繞：** commit 路徑只掃 staged 增量並設效能預算；全歷史、build 產物與依賴掃描放在安裝、手動掃描或背景工作。原型驗收必須量大型 repo 的高百分位延遲與停用率，不能只量平均速度。

### 5. 本機例外資料可能變成新的敏感資料

**為什麼會擋：** 誤報記憶若保存原始 key、片段、完整路徑或可逆內容，就建立一個集中線索庫。規劃只寫「存本機、不上傳」，尚未定義存什麼；本機不等於安全。[依據：`PLAN.md`「技術基座決定」；`DECISION.md`「低誤報＋可操作」]

**怎麼繞：** 只存規則 ID、不可逆指紋與最少範圍；預設不保存原始命中內容；提供查看、刪除與 repo 級例外；例外檔若進版控，不得含可回推密鑰的材料。這是資安資料模型，應在 GUI 前先定。

# 四、最該先砍掉的一件事

**結論：先砍「第一個付費功能：一鍵修掉前端洩漏的 key」。這一刀最能提高成功率。**

它同時踩中四個問題：不是確定性工作、無法由階段一數據驗證、容易破壞應用程式、會把小工具拖進框架與部署商的無底洞。更嚴重的是，它若把 key 搬到一個沒有認證的後端代理，可能把「密鑰外洩」改造成「公開濫用端點」，產品反而創造新漏洞。[依據：`PLAN.md`「階段二」與判準表；`research/03-X社群需求盤點.md` §2.1 卡點 C；`DECISION.md`「三件不能忍」第 2 條]

付費驗證應改成階段一能力的自然升級：macOS 批次發現 repo、正確安裝 hook、一次掃歷史、互動式分類、框架感知的處理指引、revoke 導航與複掃證明。偵測與建議可以確定；涉及架構改寫時只顯示差異與限制，不承諾一鍵完成。這樣付費結果才真正驗證「非專業使用者是否願意為低摩擦的確定性安全流程付錢」。[依據：`DECISION.md`「四個必要能力」「商業模式」；`research/01-開源競品-gitleaks生態.md`「空位判斷」；`research/02-商業競品與定價.md` §4]

**判斷會反轉的條件：** 僅在範圍縮到少數明確框架與部署組合、可自動跑完測試、可證明不新增公開代理風險，且真實使用者先為受控原型付費時，才把它作為獨立修復器重新加入；不能再當桌面版首個必押功能。
